A blog article should be validated and rendered before deployment. Its view count must change afterward. The site compiles content with Astro and gives the counter a narrow Solid, Elysia, and SQLite path:

```mermaid center
flowchart LR
  MDX["Localized MDX"] --> Collection["Astro content collection"]
  Collection --> Filter["Publication filter"]
  Filter --> Paths["Static route generation"]
  Paths --> HTML["Article and archive HTML"]

  Browser["Hydrated Solid island"] --> API["Elysia view API"]
  API --> SQLite["SQLite totals and dedupe state"]
  SQLite --> Browser
```

Astro owns content identity, locale selection, navigation, and publication. SQLite owns the counters. If the API fails, the article still renders.

## Compile the content contract before generating routes

Astro's collection schema is the first boundary. [`web/content.config.ts`](https://github.com/ErickCReis/ErickCReis/blob/main/web/content.config.ts) discovers both Markdown and MDX and converts `date` into a `Date` while validating every other frontmatter field:

```ts
const blog = defineCollection({
  loader: glob({
    base: "./web/content/blog",
    pattern: "**/*.{md,mdx}",
  }),
  schema: z.object({
    title: z.string(),
    description: z.string(),
    date: z.coerce.date(),
    tags: z.array(z.string().trim().min(1)).default([]),
  }),
});
```

This makes malformed frontmatter a build error rather than a partially rendered production page. The archive can derive tag filters and sort entries from typed data; the detail route can call `render(post)` and emit the MDX body as static HTML.

The schema does not require non-empty copy, constrain tag vocabulary, enforce unique dates, or verify locale pairs.

## Treat the source filename as content identity

The two localized files for one article are:

```text
the-blog-layer-static-pages-live-view-counts.mdx
the-blog-layer-static-pages-live-view-counts.pt-BR.mdx
```

[`web/lib/blog.ts`](https://github.com/ErickCReis/ErickCReis/blob/main/web/lib/blog.ts) derives two identities from those names:

```ts
export function getBlogSlug(entry: BlogEntry) {
  const sourceName = getSourceName(entry);

  for (const suffix of localeSuffixes) {
    if (sourceName.endsWith(suffix)) {
      return sourceName.slice(0, -suffix.length);
    }
  }

  return sourceName;
}

export function getBlogViewKey(entry: BlogEntry) {
  return getSourceName(entry);
}
```

The public slug removes a recognized non-default locale suffix, so both variants map to the same route-shaped identifier. The view key preserves the full source name, so the English and Portuguese articles accumulate independent totals:

| Concern | English | Portuguese |
| --- | --- | --- |
| Source identity | `the-blog-layer-…` | `the-blog-layer-….pt-BR` |
| Public path | `/blog/the-blog-layer-…` | `/pt-BR/blog/the-blog-layer-…` |
| Counter key | `the-blog-layer-…` | `the-blog-layer-….pt-BR` |

Keeping the locale in the counter key avoids silently merging audiences. It also means renaming a source file creates a new counter identity; there is no alias or migration mechanism connecting the old key to the new one.

Locale pairing is convention-based. For a requested locale, `getBlogEntry` first looks for `${slug}.${normalizedLocale}` and then falls back to the unsuffixed source:

```ts
return (
  visibleEntries.find((entry) => getSourceName(entry) === `${slug}.${normalizedLocale}`) ??
  visibleEntries.find((entry) => getSourceName(entry) === slug)
);
```

That fallback prevents a missing translation from becoming a missing route. The tradeoff is that a Portuguese URL may render English content when its `.pt-BR` file does not exist. The build does not currently report incomplete locale pairs.

## Generate only routes visible to that build

The detail page's `getStaticPaths` takes every visible logical slug and produces its Cartesian product with the configured locales:

```ts
const slugs = [...new Set(filterPublishedEntries(entries, options).map(getBlogSlug))];

return locales.flatMap((locale) =>
  slugs.map((slug) => ({
    params: {
      locale: locale === defaultLocale ? undefined : locale,
      slug,
    },
    props: { locale, slug },
  })),
);
```

The default locale omits the URL prefix; other locales receive one through the optional catch-all route. The archive applies the same publication filter and then selects at most one source per logical slug, preferring an exact localized source over the default fallback. Using the same selection functions for route generation, archive links, article navigation, and counter keys prevents those consumers from inventing slightly different identities.

Publication is a calendar comparison, not a timestamp comparison. [`web/lib/blog-publication.ts`](https://github.com/ErickCReis/ErickCReis/blob/main/web/lib/blog-publication.ts) reads the frontmatter date as a UTC calendar key and compares it with the current date in `America/Sao_Paulo`:

```ts
export function isBlogPostPublished(date: Date, now = new Date()) {
  return getScheduledDateKey(date) <= getPublicationDateKey(now);
}
```

Both the archive and detail route pass `includeScheduled: true` only in development. Production builds exclude future entries from the archive and from `getStaticPaths`; development builds expose them for review.

This is scheduled compilation, not runtime scheduling. A build produced on August 21 does not reveal the article when São Paulo reaches August 22. A new build must run on or after the publication date. Conversely, once a route is emitted, changing the server clock does not retract it. The publication date should therefore be understood as a build input.

## Keep the client boundary narrower than the document

The archive and article use different client behaviors.

The archive renders every title, description, date, tag, link, and a `-- views` placeholder into HTML. A `client:only="solid-js"` hydrator returns no DOM of its own; on mount it finds all `[data-post-view-count]` spans and makes one batch request for their keys. It then replaces each placeholder:

```ts
void fetchPostViewCounts(props.slugs)
  .then((result) => {
    for (const placeholder of placeholders) {
      const slug = placeholder.dataset.postViewCount;
      if (!slug) continue;

      placeholder.textContent = formatViewCountLabel(result[slug] ?? 0);
    }
  })
  .catch(() => {
    for (const placeholder of placeholders) {
      placeholder.hidden = true;
      placeholder.textContent = "";
    }
  });
```

The article uses `PostViewCounter`, also as a client-only Solid island. It performs the write only after the document is visible. A background tab waits for `visibilitychange`, reducing counts caused by speculative navigation or a tab the reader never foregrounds.

Without JavaScript, the article remains readable and the archive keeps its placeholder. Failed archive reads hide the labels, and failed article writes hide the counter. An `isDisposed` guard prevents signal updates after unmount.

The request itself is not aborted on unmount, and visibility is only a coarse reading signal. A foreground tab is counted even if the visitor immediately leaves, while a reader with JavaScript disabled is never counted.

## Validate the transport independently of the UI

The browser and server share Valibot request schemas from [`shared/blog/views.ts`](https://github.com/ErickCReis/ErickCReis/blob/main/shared/blog/views.ts):

```ts
export const blogPostSlugSchema = v.pipe(
  v.string(),
  v.minLength(1),
  v.maxLength(160),
  v.regex(/^[A-Za-z0-9]+(?:[./_-][A-Za-z0-9]+)*$/),
);

export const blogPostQueryRequestSchema = v.object({
  slugs: v.pipe(v.array(blogPostSlugSchema), v.minLength(1), v.maxLength(100)),
});
```

`GET /blog/views` reads up to 100 keys in one query. `POST /blog/views` accepts one key and registers a view. Both responses set `cache-control: no-store`; the client also requests `cache: "no-store"`. This avoids serving an old counter from the browser or an intermediary cache.

The API validates key shape but does not verify that a key belongs to the built collection. Any caller can create rows for a well-formed invented key. There is also no rate limiter beyond per-cookie deduplication, so clients that discard cookies can inflate totals.

## Make deduplication and aggregation one transaction

The first `POST` assigns an opaque visitor ID matching `ct_[A-Za-z0-9_-]{21}`. Elysia stores it in a strict same-site, HTTP-only cookie with a one-year lifetime and enables `Secure` in production. Client JavaScript sends the cookie but cannot read or select its value.

SQLite stores four projections:

| Table | Primary key | Retention and purpose |
| --- | --- | --- |
| `blog_post_view_totals` | `slug` | Permanent total |
| `blog_post_view_visitors` | `slug, visitor_id` | 24-hour dedupe state |
| `blog_post_daily_views` | `date, slug` | Daily report aggregate |
| `blog_post_weekly_views` | `week_start, slug` | Sunday-to-Saturday aggregate |

`registerPostView` runs an immediate SQLite transaction. It calculates a 24-hour cutoff, removes stale visitor rows, checks the current visitor-and-key pair, and returns the existing total when that pair is still recent. Otherwise it upserts the dedupe row and increments the total, daily, and weekly projections:

```ts
tx.insert(blogPostViewTotals)
  .values({ slug, totalViews: 1, updatedAtMs: nowMs })
  .onConflictDoUpdate({
    target: blogPostViewTotals.slug,
    set: {
      totalViews: sql`${blogPostViewTotals.totalViews} + 1`,
      updatedAtMs: nowMs,
    },
  })
  .run();
```

The daily date and week start are calculated in the same São Paulo timezone used by reporting. At midnight, a cron job builds either the previous day's report or, on Sunday, the previous Sunday-to-Saturday weekly report. These report tables are denormalized at write time; reports do not scan visitor rows or reconstruct history from the permanent total.

`behavior: "immediate"` acquires SQLite's write reservation before the read-modify-write sequence. Concurrent writers cannot both observe an absent dedupe row and independently increment outside that sequence. The four projections and the dedupe token commit together: an exception before commit rolls the transaction back, while a successful response reflects a committed total selected inside the transaction.

This is atomic within one SQLite database, not a distributed exactly-once protocol. Durability still depends on the database file and its storage configuration. Multiple application instances need to share the same database with compatible locking semantics; independent SQLite files would produce divergent totals. Opportunistic cleanup also means expired visitor rows remain until a later successful write.

## Define what the number means

The displayed value counts accepted `(content key, visitor cookie, 24-hour window)` writes committed to this database. It does not represent unique people or sessions.

That definition exposes the system's limits:

- Clearing or blocking the cookie creates a new visitor identity.
- Several people sharing one browser profile are deduplicated together.
- One person using multiple browsers or devices is counted multiple times.
- View totals split when a localized source or filename uses a different key.
- The visitor table permits short-term cross-article correlation through the same opaque ID, even though it stores no IP address, account, referrer, or user agent.
